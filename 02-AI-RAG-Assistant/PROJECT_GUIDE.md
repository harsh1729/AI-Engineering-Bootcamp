# Project Guide — 02 AI RAG Assistant

This document defines the vision, architecture principles, and working rules for this project. It is the source of truth for both human contributors and AI coding assistants. Read it before making changes.

---

## Project Vision

Build a production-quality **Retrieval-Augmented Generation (RAG) Assistant** — a system that lets users upload documents, ask questions about them, and receive grounded, cited answers generated by an LLM.

The project is built **incrementally, one phase at a time**, mirroring how a real production system is developed: small, reviewable steps rather than a large upfront skeleton. Every phase should leave the system in a working, testable state.

This project is also a vehicle for practicing production software engineering: clean architecture, separation of concerns, testability, and deliberate technical decisions — not just "getting it to work."

---

## High-Level Roadmap

The roadmap below is directional, not a commitment to specific folders or files. Each phase is scoped and implemented only when we actually start it.

1. **Foundation** — project scaffold, conventions, and rules (this phase).
2. **Backend core** — minimal API service wired to `01-LLM-SDK` for a single end-to-end LLM interaction (no retrieval yet).
3. **Document ingestion** — upload and process documents into retrievable chunks.
4. **Retrieval** — embedding storage and similarity search over ingested documents.
5. **RAG generation** — combine retrieval with LLM generation, including citations.
6. **Conversation & tooling** — multi-turn conversations, tool calling, streaming responses to clients.
7. **Frontend** — user-facing interface for upload, chat, and citations.
8. **Production hardening** — auth, observability, evaluation, deployment.

Later phases may reshape earlier ones as we learn more. The roadmap is expected to evolve.

## Architecture Principles

1. **`01-LLM-SDK` is the only path to LLM providers.** This project must never import or call the OpenAI, Anthropic, or Google GenAI SDKs directly. All LLM interactions (generation, streaming, tool calling) go through `01-LLM-SDK`'s provider abstraction.
2. **Providers own orchestration** (inherited convention from `01-LLM-SDK`): request lifecycle, retries, streaming, and tool-calling flow are the SDK's responsibility, not this project's.
3. **Separation of concerns.** API layer, business logic, retrieval, and LLM interaction stay in distinct modules. No layer reaches past its neighbor.
4. **Incremental structure.** Folders and modules are created when a phase actually needs them — not in anticipation of future phases.
5. **Explicit boundaries over cleverness.** Prefer clear, direct code over abstractions that don't yet have two or more real use cases.
6. **Config over hardcoding.** Environment-specific values (paths, model names, limits) belong in configuration, not scattered in code.

---

## Coding Standards

- **Python 3.13**, type-hinted throughout.
- Use **Pydantic models** for request/response data shapes, consistent with `01-LLM-SDK`.
- Keep modules small and single-purpose; prefer several focused files over one large one.
- No narrating comments (e.g. `# increment counter`). Comments explain *why*, not *what*.
- No dead code, commented-out blocks, or placeholder business logic left in the codebase.
- Tests live in `backend/tests/` and are added alongside the feature they cover, not after the fact.
- Dependencies are pinned in `requirements.txt` and only added when a phase requires them.

---

## Development Rules

1. **Build only the current phase.** Do not create folders, files, or code for future phases "while we're at it."
2. **No speculative abstractions.** Don't generalize until there are at least two concrete use cases.
3. **No new dependencies without discussion.** Adding a package is an architectural decision.
4. **Every phase should run.** Avoid leaving the project in a broken or half-wired state between phases.
5. **Ask before assuming.** If a requirement is ambiguous, ask rather than guess.
6. **Discuss architecture before writing code** for any non-trivial change (new module boundaries, data flow, storage choices).

---

## Rules for AI Coding Assistants (Cursor / Claude Code)

- **Never call OpenAI, Anthropic, or Google GenAI SDKs directly.** All LLM interactions must go through `01-LLM-SDK`'s `ProviderFactory` / provider abstraction.
- **Do not create folders, files, or scaffolding for phases that haven't started.** Build exactly what the current step requires.
- **Do not add placeholder business logic, TODOs-as-code, or stub endpoints** "for later." Empty phases stay unbuilt, not half-built.
- **Modify only the files necessary for the requested task.** Do not refactor unrelated working code.
- **Do not install or add packages** without the change being explicitly requested or agreed upon.
- **Ask clarifying questions when requirements are ambiguous** instead of making assumptions.
- **Discuss architecture and approach before proposing code** for any change with meaningful design decisions or trade-offs.
- **Match existing conventions** from `01-LLM-SDK` where this project touches it (naming, structure, provider abstraction usage).

---

## Notes

- **All LLM interactions must go through `01-LLM-SDK`.** This project has no direct dependency on any LLM vendor SDK — only on the local `01-LLM-SDK` package.
- **Folders are introduced only when they are actually needed.** The scaffold created in the foundation phase is intentionally minimal; structure grows with the project, not ahead of it.
